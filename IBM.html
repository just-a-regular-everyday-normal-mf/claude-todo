1. What is actually known about this test (and what is not)

Backed by candidate reports (PracHub write-ups, Aug 2026, and Glassdoor)

  • 80 minutes total, strict proctoring (one monitor, full-screen), and a slow web IDE where you cannot run single tests, so full runs eat time.
  • You pick a framework at the start (Django, Spring Boot or Node). You have already been given Spring Boot (Java).
  • Question 1 was LeetCode 1797, Design Authentication Manager. Another candidate reported an easy-to-medium binary search question instead, so expect a design, hash-map or binary-search style problem, not exotic DSA.
  • Question 2 was a pre-built ticket-booking web app with broken backend code. Topics: REST behaviour, caching, pagination. A candidate with the Django version of the same 80-minute test listed the actual bugs: search filters not chained, pagination crashing on non-positive page or page_size, and cache not evicted when an event is created or edited. Expect the same bug classes in Spring Boot.

Not verified (treat as guesses)

  • Gemini's claims of 40 minutes per section, Spring Boot 3.3 and ConcurrentMapCacheManager. I found no source for these. Prepare for a shared 80-minute timer.
  • ChatGPT's items 4-11 (e.g. Maximize Revenue from Depleting VM Stock, Break Adjacent Duplicate Characters) and "Maximum Number of Valid Pairs". I could not confirm them, and the last is not a LeetCode title I recognise. They are optional extras, not core.
  • No report confirms the campus 2026-27 test uses exactly these questions. It is the same company, same length and same section names, so it is very likely the same question family.

Plan logic: half the marks are a debugging task, so the plan is half hands-on Spring Boot (build your own ticketing app, then break and fix it) and half DSA focused on design and hash-map problems.

Day 1: Foundations and the reported Question 1

Block A: DSA (about 70 min)

  • ★ LeetCode 49 Group Anagrams 15 min
  • ★ LeetCode 560 Subarray Sum Equals K 20 min
    Prefix sum plus HashMap.
  • ★ LeetCode 1797 Design Authentication Manager, three passes 35 min
    • Pass 1: HashMap<String,Integer> of tokenId to expiry; count by scanning.
    • Pass 2: LinkedHashMap with lazy purge. Time only increases and TTL is constant, so remove-then-put on renew keeps entries sorted by expiry. Pop expired entries from the head, then the size is your count (amortized O(1)).
    • Pass 3: edge rules. A token expiring at time t is already expired for any action at time t (use expiry > now). Renew on a missing or expired token is ignored. Check whether generate on an existing id replaces it, and what the statement says about time ordering.

Block B: Spring Boot baseline (about 75 min)

  • ★ Create a project at start.spring.io: Java 17, Maven, dependencies Spring Web, Spring Data JPA, H2, Validation, Spring Cache. Skip Lombok so you practise writing getters.
  • ★ Model "TicketHub": Event(id, name, date, venue, totalSeats, availableSeats) and Booking(id, eventId, quantity, status, idempotencyKey), with repositories, a service layer and controllers.
  • ★ Endpoints: GET /events, GET /events/{id}, POST /events, POST /events/{id}/bookings, DELETE /bookings/{id}.
  • ★ Run it, hit every endpoint with curl or Postman, then git init and commit as "baseline" so you can break and fix it later.

Block C (about 20 min)

  • ★ On the IBM test page, click Sample Test. Check full-screen, one monitor, that the Spring Boot IDE loads, and how Run vs Submit behave.
  • ★ Skim the PracHub write-ups linked in the Resources section.
  • Flashcards (10 min): HashMap internals, equals/hashCode, ArrayList vs LinkedList.

Day 2: Design problems and REST correctness

Block A: DSA (about 70 min)

  • ★ LeetCode 146 LRU Cache 30 min
    Do HashMap plus doubly linked list first, then the LinkedHashMap removeEldestEntry version.
  • ★ LeetCode 380 Insert Delete GetRandom O(1) 20 min
  • ★ LeetCode 1396 Design Underground System 20 min

Block B: Status codes, validation, errors (about 85 min)

  • ★ Add a @RestControllerAdvice GlobalExceptionHandler: not found → 404, validation failure → 400, sold out or insufficient seats → 409, bad argument or type mismatch → 400.
  • ★ POST returns 201 with a Location header, DELETE returns 204, and an unknown id returns 404 (not 200 with null).
  • ★ Add @Valid plus constraints on request DTOs (@NotBlank, @Min(1)) and handle missing or invalid @RequestParam values.
  • ★ Write at least 8 MockMvc tests (@WebMvcTest plus @MockBean), one per status code path.
  • Read: Baeldung "Exception Handling for REST with Spring" and reflectoring "Testing MVC Web Controllers" (see Resources).

Block C (about 15 min)

  • Flashcards: == vs equals, String vs StringBuilder vs StringBuffer, checked vs unchecked exceptions.

Day 3: Binary search and pagination

Block A: DSA (about 60 min)

  • ★ LeetCode 704 Binary Search and 35 Search Insert Position 15 min total
  • ★ LeetCode 34 Find First and Last Position of Element in Sorted Array 15 min
  • ★ LeetCode 33 Search in Rotated Sorted Array 15 min
  • ★ LeetCode 981 Time Based Key-Value Store 15 min
  • ☆ LeetCode 875 Koko Eating Bananas

Block B: Pagination (about 90 min)

  • ★ GET /events?page=&size=&sort= using Pageable or PageRequest. Return a DTO with content, page, size, totalElements, totalPages.
  • ★ Edge cases: page < 0, size <= 0, size above a cap (say 100), non-numeric values, page beyond the last page (empty content). Decide the behaviour (400 or fallback to defaults) and know which one Spring's own Pageable resolver gives you versus a plain @RequestParam int.
  • ★ Deterministic ordering: always add a tie-breaker (Sort.by("date").and(Sort.by("id"))). Verify no row is duplicated or skipped across page boundaries.
  • ★ Optional filters (name, venue, date range) that combine with each other and with paging. The Django bug was filters not being chained.
  • ★ Six tests: first page, last partial page, beyond last page, invalid params, sort order, filter plus page together.
  • Watch/read: the loizenai pagination video and the Dan Vega or codejava tutorials (see Resources).

Block C (about 15 min)

  • Flashcards: DI and IoC, bean scopes, bean lifecycle.

Day 4: Heaps and caching

Block A: DSA (about 60 min)

  • ★ LeetCode 1845 Seat Reservation Manager 15 min
    Min-heap, and it is ticket-themed.
  • ★ LeetCode 2034 Stock Price Fluctuation 25 min
    TreeMap, or two heaps with lazy deletion.
  • ★ LeetCode 347 Top K Frequent Elements 15 min
  • ☆ LeetCode 703 Kth Largest Element in a Stream

Block B: Caching (about 90 min)

  • ★ Add @EnableCaching. Put @Cacheable("event", key="#id") on getEvent. Prove it works by verifying the repository is called once across two reads.
  • ★ Reproduce the stale-data bug: update an event, then GET it and see the old value. Fix with @CachePut or @CacheEvict on update and delete, and @CacheEvict(allEntries=true) on create for any cached list.
  • ★ If you cache lists, the key must include page, size, sort and filters, or do not cache lists at all.
  • ★ Learn the classic cache traps: calling a cached method from the same class (proxy bypass), annotations on private methods, missing @EnableCaching, wrong cache name, caching a mutable entity.
  • ☆ Know the difference between the default ConcurrentMapCacheManager and Caffeine or Redis (concepts only).
  • Watch: MVP Java "Spring Caching with Caffeine Cache" (annotations overview part only) and read the howtodoinjava cache article.

Block C (about 15 min)

  • Flashcards: @Transactional and propagation, lazy vs eager loading, JPA entity relationships.

Day 5: Concurrency, overselling, idempotency, timed re-solves

Block A: DSA (about 60 min)

  • ★ Timed re-solve from a blank file, no peeking: LeetCode 1797 20 min and LeetCode 146 25 min
  • ★ LeetCode 1146 Snapshot Array 15 min
    Binary search plus a map.
  • ☆ LeetCode 2349 Design a Number Container System

Block B: Correct under load (about 90 min)

  • ★ Prevent overselling three ways and know the trade-offs: (1) atomic UPDATE ... SET available = available - :qty WHERE id = :id AND available >= :qty and check rows updated, (2) @Version optimistic locking with a retry, (3) @Lock(PESSIMISTIC_WRITE).
  • ★ Idempotent booking: an Idempotency-Key header or unique constraint, so a retried request returns the original booking and never creates a duplicate.
  • ★ @Transactional on the service layer, rollback on runtime exceptions, readOnly=true for queries.
  • ★ Concurrency test: 50 threads each book 1 seat on a 10-seat event and exactly 10 succeed.
  • ★ Cancelling a booking restores seats exactly once, and cancelling twice does not double-restore.

Block C (about 15 min)

  • Flashcards: REST idempotency (GET, PUT and DELETE idempotent, POST not), HTTP status code cheat sheet, multithreading and synchronization.

Bug checklist (my synthesis of the reported bug classes)

  • REST and routing: wrong mapping annotation or path variable name, wrong status code (200 vs 201 vs 204 vs 404 vs 409), returning null instead of 404, missing @RequestBody or @Valid, wrong HTTP method.
  • Pagination: zero-based vs one-based page, crash on invalid page or size, no tie-breaker in sort, wrong totalPages or totalElements, size not capped, filter parameters not combined.
  • Caching: missing @EnableCaching, no eviction on create, update or delete, key collision or key missing paging and filter params, self-invocation bypassing the proxy.
  • Correctness under concurrency: check-then-act race on seat availability, duplicate bookings on retry, @Transactional missing or on the wrong layer, double restore on cancel.

Test-day checklist

  • One monitor, close other apps and tabs, charger plugged in, stable internet, run the portal's compatibility check.
  • Choose Spring Boot (Java) at the framework prompt.
  • Read the full statement and all tests before touching code.
  • Budget about 30 to 35 minutes for the design problem. Run the whole suite early on the Spring Boot task and avoid wasting runs.
  • Write your own code. IBM runs originality checks and a correct answer can still be flagged.
